# 03 — статический вызов

```bash
cd ~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1/linux/SP_lib
g++ -fPIC -shared SP.cpp -o SP.so
cd ../SP_03
cp ../SP_lib/SP.so .
g++ main.cpp SP.so -o SP_03
LD_LIBRARY_PATH=. ./SP_03
```

`-fPIC` — Position Independent Code. Обычный компилятор запекает абсолютные адреса в машинный код на этапе линковки: исполняемый файл загружается по фиксированному адресу, и это работает. `.so` так не может — одна библиотека загружается в десяток процессов по разным адресам. `-fPIC` заменяет обращения к глобалам на относительные через GOT (Global Offset Table), на aarch64 — через пары инструкций `ADRP`/`ADD`. Плата: лишняя косвенность, 1–3% медленнее. На x86-64 сборка без `-fPIC` обычно проходит, но при линковке с PIE-исполняемым файлом падает с `relocation R_X86_64_32S against ... can not be used when making a PIE object`. Флаг не опционален.

`-shared` — переключает компоновку на создание разделяемого объекта: линкер получает `-Wl,-soname`, определяется макрос `__PIC__`, неопределённые символы разрешаются молча (`-Wl,--allow-shlib-undefined` по умолчанию), точка входа `main` не требуется. Без него `g++ SP.cpp -o SP.so` соберёт попытку сделать исполняемый файл, и линкер ругнётся на отсутствие `main`.

`SP.so` отдельным аргументом в `g++ main.cpp SP.so -o SP_03` — файл-вход для линкера, не библиотека по короткому имени. Линкер читает из него `.dynsym` и закрывает неопределённые ссылки на `sum`, `sub`, `mul`, `div`. Имя буквальное: файл называется `SP.so`, поэтому `-lSP` не сработает — искал бы `libSP.so`.

`LD_LIBRARY_PATH=.` — переменная окружения, читаемая загрузчиком `ld-linux-aarch64.so.1`. Порядок поиска: `DT_RPATH` бинарника → `LD_LIBRARY_PATH` → `DT_RUNPATH` → кэш `ld.so.cache` → системные каталоги `/lib`, `/usr/lib`. Знак `.` добавляет текущий каталог. Без неё загрузчик доходит до кэша и системных папок, `linux/SP_lib` там нет, и падает с `error while loading shared libraries: SP.so: cannot open shared object file`. Переменная игнорируется для setuid-программ.

Вывод:

```
SP_03: static link (SP.so)
sum(10, 5)  = 15
sub(10, 5)  = 5
mul(10, 5)  = 50
div(10, 5)  = 2
```

```bash
cd ~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1/linux/SP_03
readelf -d SP_03 | grep SP.so
```

```
 0x0000000000000001 (NEEDED)             Shared library: [SP.so]
```

`readelf` из пакета `binutils`. `-d` — секция `.dynamic`, таблица в ELF, из которой загрузчик берёт зависимости. Запись `NEEDED` (`DT_NEEDED`) означает, что `SP.so` вписан в бинарник на этапе сборки и загрузится автоматически при старте, до `main`.

# 04 — динамический вызов

```bash
cd ~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1/linux/SP_lib
g++ -fPIC -shared SP.cpp -o SP.so
cd ../SP_04
cp ../SP_lib/SP.so .
g++ main.cpp -ldl -o SP_04
./SP_04
```

`-ldl` — линкеру передаётся `libdl.so`. Исторически `dlopen`/`dlsym` жили в отдельной библиотеке, без `-ldl` сборка падала с `undefined reference to 'dlopen'`. С glibc 2.34 (2021) они переехали в саму `libc`, и `libdl` стал пустой заглушкой — флаг формально не нужен, но оставлять его безопасно и переносимо.

`SP.so` в команде линковки отсутствует принципиально. Приложение не знает о библиотеке на этапе сборки: неопределённые ссылки не возникают, потому что адреса функций берутся в рантайме. Путь задан строкой в `dlopen("./SP.so")`, поэтому `LD_LIBRARY_PATH` не требуется.

```c
typedef int (*BinFunc)(int, int);
BinFunc sum = (BinFunc)dlsym(h, "sum");
```

`dlsym` возвращает `void*` — универсальный указатель без типа. Приведение `(BinFunc)` обязательно: без него результат нельзя вызвать как функцию. Имя ищется по строке, поэтому в `SP.cpp` обязателен `extern "C"` — иначе компилятор C++ исказит экспорт до `_Z3sumii`, и `dlsym("sum")` вернёт NULL.

Вывод:

```
SP_04: dynamic link (dlopen)
sum(10, 5)  = 15
sub(10, 5)  = 5
mul(10, 5)  = 50
div(10, 5)  = 2
```

```bash
cd ~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1/linux/SP_04
readelf -d SP_04 | grep SP.so
```

Вывод пустой: `SP.so` не встречается ни в одной записи `.dynamic`. Контраст с заданием 03.

# 07 — C#, DllImport

```bash
export DOTNET_ROOT="$HOME/.dotnet"; export PATH="$HOME/.dotnet:$PATH"
cd ~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1/linux/cs/SP_07
dotnet publish -c Release -r linux-arm64 --self-contained true -p:PublishSingleFile=true
cd bin/Release/net8.0/linux-arm64/publish
cp ~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1/linux/SP_lib/SP.so .
ls -lh SP_07 SP.so
./SP_07
```

`DOTNET_ROOT` — SDK установлен не в системный префикс, а в `~/.dotnet`. Компилятор и хост .NET берут из этой переменной путь к корню установки.

`-c Release` — конфигурация без отладочных символов, с оптимизацией. В `Debug` сборка медленнее, но пригодна для отладчика.

`-r linux-arm64` — Runtime Identifier, целевая платформа. Влияет на выбранный нативный хост и на `System.Runtime.InteropServices`, который ищет `libSystem.Native.so` под нужную архитектуру. Без него publish остаётся framework-dependent.

`--self-contained true` — рантайм .NET упаковывается в выходной каталог, приложение запускается на машине без установленного .NET. Цена: 71 МБ вместо нескольких сотен килобайт.

`-p:PublishSingleFile=true` — свойство MSBuild, склеивает managed-сборки и нативные хосты в один исполняемый файл. Исполняемый файл один, но `SP.so` остаётся отдельным: нативные библиотеки бандлер не встраивает, они грузятся с диска.

Путь `bin/Release/net8.0/linux-arm64/publish` — `net8.0` соответствует `<TargetFramework>` в `.csproj`, `linux-arm64` подставляется из `-r`.

`ls -lh SP_07 SP.so` — контроль: `SP.so` ≈ 69 КБ, `SP_07` ≈ 71 МБ. 69 КБ — наша C++-библиотека, большой файл — обёртка с .NET внутри. Библиотека обязана лежать в одном каталоге с программой: путь `DllImport("SP")` резолвится через `NATIVE_DLL_SEARCH_DIRECTORIES`, куда .NET добавляет каталог исполняемого файла, и через `NATIVE_DLL_SEARCH_SYSTEM_DIRECTORIES`. Текущий рабочий каталог в этот список не входит.

Вывод:

```
Сложение в C++/DLL/SO: 15
Вычитание в C++/DLL/SO: 5
Умножение в C++/DLL/SO: 50
Деление в C++/DLL/SO: 2
```

# 08 — C#, dlopen

```bash
export DOTNET_ROOT="$HOME/.dotnet"; export PATH="$HOME/.dotnet:$PATH"
cd ~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1/linux/cs/SP_08
dotnet publish -c Release -r linux-arm64 --self-contained true -p:PublishSingleFile=true
cd bin/Release/net8.0/linux-arm64/publish
cp ~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1/linux/SP_lib/SP.so .
ls -lh SP_08 SP.so
./SP_08
```

`NativeLibrary.Load("./SP.so")` — обёртка над `dlopen` из `libSystem.Native.so`. `NativeLibrary.GetExport` — обёртка над `dlsym`. `Marshal.GetDelegateForFunctionPointer` превращает `IntPtr` в вызываемый делегат: `IntPtr` хранит адрес, но не сигнатуру, делегат её описывает, и рантайм строит обратный вызов с правильной передачей аргументов.

Строка `"./SP.so"` — относительный путь, резолвится через `open()` от текущего рабочего каталога процесса, а не от каталога программы. Отсюда запуск из `publish`: из папки проекта путь указывает на несуществующий файл, и `Load` возвращает `IntPtr.Zero`.

Вывод:

```
Сложение в C++/DLL/SO: 15
Вычитание в C++/DLL/SO: 5
Умножение в C++/DLL/SO: 50
Деление в C++/DLL/SO: 2
```

# 03 + 04 + 07 + 08 одним блоком

```bash
export DOTNET_ROOT="$HOME/.dotnet"; export PATH="$HOME/.dotnet:$PATH"
L=~/Documents/VisualStudioCodeRepos/SystemProgramming/lab1

(cd $L/linux/SP_lib && g++ -fPIC -shared SP.cpp -o SP.so)

(cd $L/linux/SP_03 && cp ../SP_lib/SP.so . && g++ main.cpp SP.so -o SP_03 && LD_LIBRARY_PATH=. ./SP_03)

(cd $L/linux/SP_04 && cp ../SP_lib/SP.so . && g++ main.cpp -ldl -o SP_04 && ./SP_04)

(cd $L/linux/cs/SP_07 && dotnet publish -c Release -r linux-arm64 --self-contained true -p:PublishSingleFile=true -v q --nologo && cd bin/Release/net8.0/linux-arm64/publish && cp $L/linux/SP_lib/SP.so . && ./SP_07)

(cd $L/linux/cs/SP_08 && dotnet publish -c Release -r linux-arm64 --self-contained true -p:PublishSingleFile=true -v q --nologo && cd bin/Release/net8.0/linux-arm64/publish && cp $L/linux/SP_lib/SP.so . && ./SP_08)
```

`-v q` — quiet, `--nologo` — без баннера, чтобы в выводе остались только результаты.

Подстановка `(cd X && ...)` выполняет команду в подшелле: `cd` не меняет каталог родительского терминала. Всё собирается заново, артефакты `bin/` и `obj/` не переиспользуются.
