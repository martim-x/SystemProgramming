## 1. «Как создавали проект?»

**Windows-часть (задания 01, 02, 05, 06)** — в Visual Studio 2022:

| Шаг | Что сделано |
|---|---|
| 01 | `New Project → C++ → Dynamic-Link Library (DLL)`, имя `SP` |
| | в шаблоне уже есть `pch.h` и `framework.h` — дописал в них `windows.h` |
| | в `SP.cpp` вставил функции из таблицы 1 |
| | `Build` → появились `SP.dll` и `SP.lib` |
| | `New Project → C++ → Console App`, имя `SP_01` |
| | Properties → `Linker → Input → Additional Dependencies: SP.lib` |
| | Properties → `Linker → General → Additional Library Directories: ..\SP\x64\Debug` |
| 02 | `New Project → C++ → Console App`, имя `SP_02`, **настройки линковки не менял** |
| 05 | `New Project → C# → Console App`, имя `SP_05`, Framework `.NET 8.0` |
| 06 | `New Project → C# → Console App`, имя `SP_06`, Framework `.NET 8.0` |

**Linux-часть (задания 03, 04, 07, 08)** — в терминале, без IDE:

| Задание | Команды |
|---|---|
| 03 | `g++ -c SP.cpp -o SP.o` → `g++ -shared SP.o -o SP.so` → `g++ main.cpp SP.so -o SP_03` |
| 04 | `g++ -fPIC -shared SP.cpp -o SP.so` → `g++ main.cpp -ldl -o SP_04` |
| 07 | `dotnet publish -c Release -r linux-arm64 --self-contained true -p:PublishSingleFile=true` |
| 08 | то же + запуск из папки с библиотекой |

**Ключевой момент:** файл библиотеки **один и тот же** — `SP.cpp`, `pch.h`,
`framework.h` лежат и в `windows/SP_lib/`, и в `linux/SP_lib/`. Он собирается
на обеих ОС, потому что в `pch.h` ветка с `windows.h` под `#if defined(_WIN32)`,
а на Linux она пустая.

## 3. «Как показать, что всё работает?»

Пять проверок, которые доказывают корректность. Все они внутри `demo.sh`.

### Проверка 1: библиотека экспортирует функции

```bash
nm -D ~/lab1/linux/SP_lib/SP.so | grep -E ' T (sum|sub|mul|div)$'
```

```
0000000000000604 T sum
0000000000000624 T sub
0000000000000644 T mul
0000000000000664 T div
```

Буква `T` = «функция в глобальной таблице символов». Если бы экспорта не было,
приложение не смогло бы найти функции.

### Проверка 2: задание 03 — статическая линковка доказана

```bash
readelf -d ~/lab1/linux/SP_03/SP_03 | grep NEEDED | grep SP.so
```

```
0x0000000000000001 (NEEDED)   Shared library: [SP.so]
```

`SP.so` в списке `NEEDED` = библиотека прописана в бинарнике при сборке,
загрузчик ОС подгрузит её сам при старте.

### Проверка 3: задание 04 — динамическая линковка доказана

```bash
readelf -d ~/lab1/linux/SP_04/SP_04 | grep NEEDED
```

```
0x0000000000000001 (NEEDED)   Shared library: [libstdc++.so.6]
0x0000000000000001 (NEEDED)   Shared library: [libm.so.6]
0x0000000000000001 (NEEDED)   Shared library: [libgcc_s.so.1]
0x0000000000000001 (NEEDED)   Shared library: [libc.so.6]
```

**`SP.so` здесь отсутствует** — в отличие от задания 03. Это и есть главное
доказательство: приложение не знает о библиотеке на этапе сборки, оно
загружает её в runtime через `dlopen`.

> Показывай оба вывода рядом, 03 и 04 — контраст сразу бросается в глаза.

### Проверка 4: роль `LD_LIBRARY_PATH`

```bash
cd ~/lab1/linux/SP_03
env -u LD_LIBRARY_PATH ./SP_03
```

```
./SP_03: error while loading shared libraries: SP.so: cannot open shared object file
```

Затем:

```bash
LD_LIBRARY_PATH=. ./SP_03
```

```
SP_03: static link (SP.so)
sum(10, 5)  = 15
```

**Зачем нужно:** показывает, что при статической линковке библиотека ищется
загрузчиком по имени, а он по умолчанию не смотрит в текущем каталоге.
В задании 04 это не нужно — там путь указан прямо в `dlopen("./SP.so")`.

### Проверка 5: C# вызывает нативный код

```bash
cd ~/lab1/linux/cs/SP_07/bin/Release/net8.0/linux-arm64/publish
ls -lh SP_07 SP.so
./SP_07
```

```
69K    SP.so
71M    SP_07
Сложение в C++/DLL/SO: 15
Вычитание в C++/DLL/SO: 5
Умножение в C++/DLL/SO: 50
Деление в C++/DLL/SO: 2
```

69 КБ — это наша C++-библиотека, 71 МБ — C#-обёртка. Приложение на C# вызывает
функции, написанные на C++.

## 4. Частые вопросы и ответы

**«Чем статическая линковка отличается от динамической?»**
Статическая: библиотека известна линкеру при сборке, её метаданные
прописываются в бинарник, загрузка происходит до `main`. Динамическая:
библиотека не упоминается при сборке, приложение загружает её в runtime через
`LoadLibrary`/`dlopen` и ищет функции по имени через `GetProcAddress`/`dlsym`.

**«Зачем нужен .lib для DLL?»**
Таблица имён функций для линкера. Без неё линкер не знает, что вызывать,
и выдаёт `unresolved external symbol sum`.

**«Почему .so не нужен .lib?»**
Таблица экспортов встроена в сам ELF-файл, линкер читает её прямо из `.so`.

**«Зачем `extern "C"`?»**
Без него имя функции искажается до `_Z3sumii`, и по строке `"sum"` её не найти.

**«Что делает DllMain?»**
Точка входа Windows DLL, вызывается ОС при загрузке/выгрузке. На Linux
аналог — `__attribute__((constructor))`.

**«Зачем `-fPIC`?»**
Позиционно-независимый код: загрузчик сам выбирает адрес, потому что одна
`.so` может грузиться в несколько процессов.

**«Зачем `-ldl`?»**
`dlopen`/`dlsym` живут не в libc, а в отдельной библиотеке `libdl`.

**«Что делает `LD_LIBRARY_PATH`?»**
Список каталогов, где загрузчик ищет библиотеки. Нужен в задании 03.

**«Почему библиотека `SP.so`, а не `libSP.so`?»**
Имя задано преподавателем. Поэтому линкую файлом напрямую
(`g++ main.cpp SP.so`), а не через `-lSP` — тот искал бы `libSP.so`.

**«Что такое self-contained?»**
В выходной файл вложен весь .NET. Программа не требует отдельно установленного
.NET на целевой машине.

**«Что делает `CallingConvention.Cdecl`?»**
Указывает соглашение о вызовах. Обязательно, потому что наш код скомпилирован
как C. На x64 разницы нет, на x86 без него будет `AccessViolation`.

**«Почему `div(x, 0)` возвращает 0, а не падает?»**
В коде защита `y != 0 ? x / y : 0`. В задании поведение при делении на ноль
не задано, решение осознанное — чтобы программа не падала на демонстрации.

## 6. Если что-то пошло не так

| Симптом | Причина и решение |
|---|---|
| `error while loading shared libraries: SP.so` | не задан `LD_LIBRARY_PATH=.` |
| `System.DllNotFoundException` | `SP.so` не лежит рядом с бинарником; для 08 — запускай из папки `publish` |
| `dotnet: command not found` | `export PATH="$HOME/.dotnet:$PATH"` в новом терминале |
| `Couldn't find a valid ICU package` | `sudo pacman -S icu` |
| `undefined reference to 'dlopen'` | забыт флаг `-ldl` |
| `SP_03` не запускается после `cd` | `LD_LIBRARY_PATH=.` действует только в текущем каталоге |
